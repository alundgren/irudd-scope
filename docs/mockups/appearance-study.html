The retry loop outlives its request

A canceled request still schedules the next attempt. The caller has left, but the worker keeps trying.

The loop catches every error and waits before retrying. Cancellation reaches the active request, then the catch block treats it like a temporary network failure. A new timer starts after the request has already ended. 

Request starts
  → network attempt fails
  → caller cancels
  → retry timer fires
  → another network attempt starts

Stop when the caller cancels

Check the cancellation signal before scheduling another attempt. Make the wait itself cancelable so the worker can stop while the timer is pending.

Keep retrying temporary connection failures while the request remains active. Cancellation should leave no timer and no network attempt behind.

What the check should prove

  • Cancel during a pending attempt. No later attempt starts.
  • Cancel during the retry delay. The timer is removed.
  • Let a temporary failure recover. The result reaches the caller once.

Reproduction

Use a local endpoint that fails the first request, then succeeds. Cancel the caller during the delay between the two attempts. Record the endpoint's request count before and after the timer would have fired.

The count should remain at one. If it reaches two, the canceled work is still running.
